# Deployed AWS Services

## Introduction

After completing the infrastructure deployment with Terraform, the resources required by the **Live Auction** system were created on Amazon Web Services.

The system follows a **Serverless Architecture**, in which the components are separated into independent functional layers. Each AWS service performs a specific role, including user authentication, frontend storage, content distribution, business logic processing, API management, real-time communication, data storage, and bid queue management.

Using AWS managed services reduces server administration work while improving the scalability, availability, and security of the system.

---

## AWS Services Overview

The main AWS services deployed in the system include:

| Service | Role in the system |
| --- | --- |
| **AWS IAM** | Manages Roles and Policies and controls access between AWS services. |
| **Amazon Cognito** | Manages user registration, authentication, login, and account information. |
| **Amazon S3** | Stores the built frontend and static application resources. |
| **Amazon CloudFront** | Distributes the frontend from Amazon S3 through a Content Delivery Network. |
| **AWS Lambda** | Executes business logic using the serverless model. |
| **Amazon API Gateway** | Provides REST APIs for communication between the frontend and Lambda. |
| **API Gateway WebSocket** | Maintains two-way connections and delivers real-time auction updates. |
| **Amazon DynamoDB** | Stores product, auction, bid history, and WebSocket connection data. |
| **Amazon SQS FIFO** | Receives and processes bid requests in the correct order. |

---

## Architecture Overview

The main workflow of the deployed system is:

1. The user accesses the Live Auction frontend through Amazon CloudFront.
2. CloudFront retrieves the frontend content stored in Amazon S3.
3. The user registers or signs in through Amazon Cognito.
4. The frontend sends business requests to Amazon API Gateway.
5. API Gateway authenticates the request and forwards it to AWS Lambda.
6. Lambda processes the business logic and reads or writes data in Amazon DynamoDB.
7. Bid requests are sent to Amazon SQS FIFO for ordered processing.
8. Bid results are delivered to connected users through API Gateway WebSocket.
9. AWS IAM controls access between all components in the architecture.

## Services by Architecture Layer

The AWS services are divided into functional layers to simplify deployment and management.

### Identity and Access Layer

This layer includes:

* AWS IAM.
* Amazon Cognito.

It is responsible for authenticating users and controlling access between AWS services.

### Frontend Storage and Distribution Layer

This layer includes:

* Amazon S3.
* Amazon CloudFront.

Amazon S3 stores the HTML, CSS, JavaScript, and other static resources generated by the frontend build process. CloudFront distributes these resources to users through AWS Edge Locations.

### Business Logic Layer

This layer includes:

* AWS Lambda.

Lambda Functions process the main system operations, including product management, auction management, bid processing, and WebSocket events.

### Communication Layer

This layer includes:

* Amazon API Gateway.
* API Gateway WebSocket.

The REST API handles standard business requests. The WebSocket API provides two-way communication and delivers real-time auction updates.

### Data Layer

This layer includes:

* Amazon DynamoDB.

DynamoDB stores application data and provides low-latency access for the system.

### Messaging Layer

This layer includes:

* Amazon SQS FIFO.

SQS FIFO receives bid requests and places them in an ordered queue. This reduces data conflicts when multiple users submit bids at nearly the same time.

## Relationships Between Services

| Source | Destination | Purpose |
| --- | --- | --- |
| User | CloudFront | Access the Live Auction frontend. |
| CloudFront | S3 | Retrieve frontend files and static resources. |
| Frontend | Cognito | Register, sign in, and receive authentication tokens. |
| Frontend | API Gateway | Send business requests to the backend. |
| API Gateway | Cognito | Validate tokens and access permissions. |
| API Gateway | Lambda | Forward requests to the corresponding processing function. |
| Lambda | DynamoDB | Read and write application data. |
| Lambda | SQS FIFO | Send bid requests to the queue. |
| SQS FIFO | Lambda | Invoke the bid processing function. |
| Frontend | WebSocket API | Establish a connection for real-time updates. |
| Lambda | WebSocket API | Send updated auction information to connected users. |
| IAM | AWS services | Control access between resources. |

## Verify Resources on AWS

After Terraform completes the deployment, the team signs in to the AWS Management Console and reviews the deployed resources.

The following resources should be checked:

* Cognito User Pool and App Client.
* IAM Roles and IAM Policies.
* S3 Bucket containing the frontend.
* CloudFront Distribution.
* Lambda Function list.
* REST API and its Routes.
* WebSocket API and its Routes.
* DynamoDB tables.
* SQS FIFO Queue.
* AWS Region of each resource.
* Resource names and project naming conventions.

## Result

After completing the deployment:

* The AWS services were created and managed through Terraform.
* The frontend was stored in Amazon S3 and distributed through Amazon CloudFront.
* Users were authenticated through Amazon Cognito.
* Business requests were received through Amazon API Gateway.
* Business logic was executed by AWS Lambda.
* System data was stored in Amazon DynamoDB.
* Bid requests were processed in order through Amazon SQS FIFO.
* Auction status was updated in real time through API Gateway WebSocket.
* Access between AWS services was controlled using AWS IAM.
* The components were ready for detailed verification in the following sections.
